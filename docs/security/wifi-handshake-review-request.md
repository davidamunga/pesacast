# Review request: PesaCast WiFi secure channel

We are asking for an independent review of a small, hand-composed secure channel before we call it done. It is built from standard primitives, but the composition is ours, which is the part most likely to hide a mistake.

PesaCast mirrors M-PESA SMS transactions (amounts, counterparties, balances) from an Android phone to a desktop app over a local network. Both apps are open source.

## The design in one paragraph

Each connection, both sides generate an ephemeral P-256 key pair and 16-byte nonce and exchange them in clear JSON. Both compute the ECDH shared secret and run HKDF-SHA256 with the **pairing token as salt**, `"pesacast-v2" || clientPub || serverPub || clientNonce || serverNonce` as info, producing one AES-256-GCM key per direction. Messages are binary records `counter(8) || ciphertext || tag`, with a 96-bit nonce made of four zero bytes and the counter, and associated data of one direction byte plus the counter. The client's first record `{"ready":true}` proves it holds the token; the server answers `{"status":"ok"}`. The token (256 random bits, entered by the user once) is never sent.

## Threat model

In scope: a passive or active attacker on the same network (shared WiFi, compromised device on the LAN) who does **not** know the pairing token. They should learn nothing about transaction contents, be unable to impersonate either side, and be unable to replay, reorder or inject records.

Out of scope: an attacker who knows the token or controls either endpoint; traffic analysis (existence, timing and sizes of messages); denial of service on the LAN; physical access; the BLE transport; the optional local broadcast server on `127.0.0.1`.

## Properties we believe hold

1. Confidentiality and integrity of records against a network attacker without the token.
2. Mutual authentication through the token: a party without it cannot derive the keys.
3. Forward secrecy against a later token compromise, from the ephemeral ECDH keys.
4. Replay, reordering and reflection are rejected (strict per-direction counters, direction byte in the AAD, separate keys).
5. Wrong-token attempts are detected on the server and counted per IP.

## Questions we would most like answered

1. Is mixing the token in as the HKDF **salt** (with ECDH as input key material) sound here, or should the token enter differently (e.g. as additional IKM, or via a PAKE)?
2. The server never sees proof of the token before sending its hello, so an attacker can obtain a server hello without the token. Does the later `ready` record check leave any offline-guessing or oracle risk beyond a 256-bit token's strength?
3. Is there any key, nonce or counter reuse across reconnects or across directions?
4. Is the transcript binding sufficient (public keys and nonces in `info`)? Is anything missing, such as the protocol version or the server's IP/port?
5. Is the validation of the peer public key complete on both platforms (WebCrypto `importKey`, and our explicit on-curve check on the JVM)?
6. Is the failure handling safe: error messages, close codes and timing that differ between "bad token" and "bad record"?
7. Anything you would replace with an off-the-shelf construction (TLS-PSK, Noise `NNpsk0`/`XXpsk`), and what it would cost?

## Known limitations

- Anyone who learns the token can impersonate either side. Regenerating the token on the phone revokes it.
- The `ready` record is not bound to a server challenge, only to the derived keys.
- No padding: message lengths reveal approximate transaction size.
- Not formally verified; no fuzzing of the hello parser yet.

## How to respond

Report findings privately as described in [SECURITY.md](../../SECURITY.md) (GitHub private vulnerability reporting), ordered by severity. Please do not include real transaction data or tokens; the test vectors use a fixed fake token. We will credit reviewers who want it.
